# Case4_Ornith – Single‑PC setup for GEPA vs MIPROv2 comparison

This folder contains the files needed to run Case 4 (external prompt optimizer comparison) on one machine, using the local LM Studio instance with the ornith-1.0-9B model.

## Folder layout (mirrors Case3_Qwen)

```
Case4_Ornith/
├─ case4/                DSPy‑optimizer package
│  ├─ __init__.py
│  ├─ dataset_case4.py   # generates the frozen train/val/test split + manifest
│  ├─ hermes_task_module.py   # DSPy/Hermes bridge (re‑uses real Hermes functions)
│  ├─ run_gepa.py        # GEPA driver (PC 1)
│  ├─ run_mipro.py       # MIPROv2 driver (PC 2)
│  ├─ replay_eval.py     # extracts final prompt, re‑runs frozen grader on held‑out test, prints verdict
│  └─ config_case4.yaml  # optimizer / model config (separate from Cases 1‑3)
├─ datasets/             # references the split generated by dataset_case4.py
│  ├─ case4_train.csv
│  ├─ case4_val.csv
│  ├─ case4_test.csv
│  └─ SPLIT_MANIFEST.md   # SHA‑256 hashes – must match on both machines
├─ config/               # Case‑4 config, independent of Cases 1‑3
│  └─ config_case4.yaml
├─ logs/                 # empty until runs start
│  ├─ case4_gepa_run.log
│  └─ case4_mipro_run.log
├─ skills/               # optional – contract md from Case 3, otherwise empty
│  └─ benchmark_coding_contract.md
├─ runs/                 # each optimizer creates its own sub‑folder
│  ├─ case4_gepa_run/
│  └─ case4_mipro_run/
├─ README.md             # this file
└─ (no run_rounds.ps1 – not needed for Case 4)
```

## How to get started (single PC)

1. **LM Studio** – install, load ornith‑1.0‑9B Q5_K_M, start local server on 127.0.0.1:1234.
2. **Verify the split** – open datasets/SPLIT_MANIFEST.md and confirm the three SHA‑256 hashes match the CSVs (re‑run `python case4/dataset_case4.py` if you need to regenerate).
3. **Pre‑flight smoke test** – run one manual forward call from case4/hermes_task_module.py to be sure the bridge talks to Hermes before starting the optimizer loops.
4. **Run GEPA** (PC 1):
   ```
   python case4/run_gepa.py --config case4/config_case4.yaml --run-id case4_gepa_run
   ```
5. **Run MIPROv2** (same machine, different process):
   ```
   python case4/run_mipro.py --config case4/config_case4.yaml --run-id case4_mipro_run
   ```
6. **Replay evaluation** after each finish:
   ```
   python case4/replay_eval.py --run-id case4_gepa_run
   python case4/replay_eval.py --run-id case4_mipro_run
   ```
   Each script prints a line like:
   ```
   CASE4 [GEPA|MIPRO] VERDICT: IMPROVED / NO CHANGE (ΔPass=X%, p=Y)
   ```
   and writes `runs/<run_id>/results.xlsx`.

7. **Merge the two result sheets** (or inspect them side‑by‑side) to see which optimizer, if any, produced a statistically significant improvement over the hand‑written default prompt.

## What the advisor / tester will check

- `datasets/SPLIT_MANIFEST.md` hashes match `case4_train.csv`, `case4_val.csv`, `case4_test.csv`.
- The three CSVs are **disjoint** (no task ID appears in more than one).
- `config_case4.yaml` is completely separate from the Cases 1‑3 `config.yaml`.
- `hermes_task_module.py` imports the real `HermesInterface`, `restore_workspace`, `grade` etc. (no stubs that silently no‑op).
- `run_gepa.py` and `run_mipro.py` reference `127.0.0.1:1234` for LM Studio and use the frozen trainset/valset with the correct DSPy API (correct `dspy.LM()` constructor, proper `.compile(student=..., trainset=..., valset=...)` calls, `reflection_lm` passed to GEPA, etc.).
- `replay_eval.py` extracts the final `task_prompt`, runs it (and a baseline) on the **full** `case4_test.csv` (15 tasks) through the **real Hermes pipeline** (HermesInterface → restore_workspace → hermes.exe → grade), computes ΔPass / Fisher exact p‑value, prints the exact console verdict line, and writes `results.xlsx`.

If all of the above look correct, the project is considered **setup‑complete** and you may proceed to the actual runs.

## Notes

- The split is generated once (seed = 4) and shared; do **not** regenerate on each machine.
- All optimizer rollouts use `auto="light"` and a small trainset to keep total runtime reasonable (dozens of rollouts, not hundreds).
- The verdict comparison is always **through the frozen Case‑3 grader** on the held‑out test set – not the optimizers' internal scores.
- No cross‑machine network calls; each PC talks only to its own LM Studio instance.
- `base_prompt_template` in `config_case4.yaml` is the string that `HermesTaskModule` will mutate via `.format(task_id=..., prompt=...)`; the optimizers (`GEPA` / `MIPROv2`) only ever touch this one field.
- **CRITICAL**: The `student_model.model_name` in `config_case4.yaml` (`ornith-1.0-9B`) is wired into `dspy.LM()` in both runner scripts; the resulting `LM` object is passed to `HermesTaskModule` and into the `HermesInterface` config so that `hermes.exe` actually uses Ornith 1.0 9B via LM Studio. Without this wiring, `hermes.exe` would default to whatever model it was previously configured to use.
- The `verdict_label` variable in `replay_eval.py` is intentionally named differently from the imported `verdict()` function from `analysis.metrics_engine` to avoid the variable-shadowing bug that would otherwise print a function repr instead of `IMPROVED/NO CHANGE`.
- The `student_lm` and `reflection_lm` variables in `run_gepa.py`/`run_mipro.py` are constructed with the correct `dspy.LM(model="openai/<model_name>", api_base=..., api_key=...)` signature and then passed to `HermesTaskModule` and into the `HermesInterface` config.

*If you need to regenerate the split, delete the three CSV files and `SPLIT_MANIFEST.md` from `G:\HermesBench\datasets\` and re‑run `python Case4_Ornith\case4\dataset_case4.py`.*
